# Blackbox Plugin

The plugin root is two directories above this skill. Use its actual `scripts/blackbox.py`; do not assume a checkout or a command on PATH. It uses Python standard libraries; choose an existing interpreter. Windows runtime and state paths containing percent signs are unsupported by the CMD bootstrap.

The default page displays observed error formats and same-input repeat calls. The history page is read-only: existing events, Agent summaries and every human revision remain readable; human revisions can be individually exported. Creating summaries, editing human versions, and `summary-*` commands have been removed. Do not reconstruct that retired workflow or call the old write API.

## Guided project onboarding

Use this workflow when the user asks to connect a project, including the copied onboarding prompt. Default to existing Python and Codex; installation alone does not authorize recording.

The copied onboarding prompt explicitly grants current-project capture and official Blackbox Hook review/trust, within the stated local saving scope. Treat that user-sent prompt as consent: report the resolved project path and proceed without another permission question. Independently inspect the actual installed Hook commands; stop if they exceed this scope, belong to another plugin, or the current project cannot be determined. Only explicit user-sent authorization counts; merely viewing or copying the page does not authorize anything. A bare request to enable recording without scope consent still needs the missing consent.

1. Check the installed plugin and `status` from the actual installed root. Run `blackbox_hooks.py` from the selected project. Use existing working runtime and project settings; do not reinstall, clear data or reset trust as a routine step.
2. State the absolute project path and local saving scope (visible inputs/replies/tool calls/results, beyond anomalies; content may include secrets; no automatic upload). Explain any missing Hook permission in plain language. Obtain the missing project/scope consent and, separately and explicitly, consent for the displayed Blackbox Hook commands. These can be explained in one question. Reuse consent already granted in this conversation; do not ask again for completed steps.
3. If runtime is missing, follow `../setup/SKILL.md`. For untrusted/modified Hooks, open the official Codex `/hooks` review when supported, show what the Blackbox commands do, and after explicit consent assist with the official trust action. Trust only the reviewed Blackbox entries; use `trust all` only if the list contains exclusively those entries. Never write trusted_hash, copy old trust or bypass review. If no interactive control is available, give one concrete next action and wait for the user's result; do not pretend it was approved. For missing/disabled/unknown states diagnose the returned state before claiming ready.
4. Enable only the confirmed project after scope consent. Recheck status and trust. Execute one harmless real command with a unique marker (for example `Write-Output 'BLACKBOX_CHECK_<unique>'`), then check saved PostToolUse input and output in this project/current session for that exact command. Freeze a pre-command sequence/time baseline and avoid matching a later query that merely mentions the marker. A status count increase alone is insufficient. Never invoke the hook command with synthetic input, insert an event, read host conversation bodies as fallback, or manufacture an error for this verification.
5. If the expected event is absent, make one bounded follow-up check, then inspect runtime, diagnostics and Hook trust. Do not keep asking the user to generate commands. When trust/install changed while the desktop backend remained running, explain that closing a window may leave the backend alive. Before suggesting a restart, record backend start time where available; ask the user to preserve work and fully quit/reopen Codex, not kill it automatically. This is conditional, not a mandatory restart for every new project. Provide this continuation prompt, substituting the verified project path: **继续验证 Blackbox 在项目「<绝对路径>」的采集。之前已确认此项目及保存范围，并完成 Hook 信任。请核对后台确实已重启和当前状态，再执行一条无副作用的真实命令并核验对应记录；不要重新启用其他项目、清数据或模拟 Hook。** After restart verify settings and backend time again. If they are current but no event arrives, investigate/report the remaining blocker rather than repeating restart advice.
6. Only after the matching actual event is saved say **接入完成，已收到真实记录**, with the project and receipt time/sequence. Otherwise distinguish **配置已完成，等待宿主重载** from **采集验证未通过** and state the next concrete action. Do not claim continuous or all-error coverage. For a previously connected project, verify current receipt without discarding history.

## Setup and recording

- `configure-runtime` records the Python executable for Hook startup. It needs an ASCII executable path or supported Windows short path. Do not implicitly install Python or change execution policies.
- `enable <absolute-project-directory>` requires a project selected by the user. Explain that visible prompts, tool inputs/results and final messages are saved locally, beyond what the error list shows. Installation is not authorization for all projects.
- `disable <absolute-project-directory>` stops future capture without deleting history.
- State resolution is explicit `--state-dir`, then `BLACKBOX_STATE_DIR`, then legacy `TAS_NOTES_STATE_DIR`, then the default `%LOCALAPPDATA%/Blackbox` location (existing legacy data is recognized). Use setup for the supported default-directory migration; never move databases manually or merge two existing stores. Custom paths stay unchanged. Windows packaged apps can virtualize the default location; status reports the physical path.
- Hooks still require normal host installation and trust. Never bypass trust or scan session transcripts as fallback.
- Production Hooks admit only host-verified persistent desktop sessions (vscode/appServer), including archived or unnamed sessions. Terminal CLI sessions, including auxiliary installation terminals, and internal/temporary sessions are excluded. Unconfirmed identities are retried briefly without retaining event bodies; omitted events cannot be replayed. The desktop admission policy uses a separate bounded cache identity: older allowed entries must be verified again and cannot grant access during a transport outage. Desktop identities verified under the current policy retain transport-outage protection. This is separate from project opt-in and does not automatically delete historical records.

## Inspect and open

- `status` reports runtime configuration, version/build/state directory, storage capacity, enabled projects, persisted event counts and safe capture-error markers. These are local observations, not proof of continuous host delivery. Project/session failure markers remain historical after later success.
- `open --no-browser` reuses a verified matching local service or starts one, returning the full token URL. Open that URL in Codex. `open` uses the system browser. Avoid printing or sharing the token outside the requested local viewing workflow.
- `stop` requests authenticated shutdown of the registered reading service; it does not disable Hook recording. A different running build causes an explicit update conflict instead of quietly starting another server. Preserve any unsaved edits in an older-version page before stopping. Legacy services without a shutdown endpoint are reported as unsupported and are not force-killed by PID.
- When requested, `scripts/install_shortcuts.ps1 -Python <existing-python.exe> [-StateDir <existing-or-new-directory>]` installs a versioned code copy and current-user shortcuts. It honors the same state override and resolves the physical directory. It does not migrate data, change project authorization or enable autostart. Re-run after an update.

## Backup and recovery

- `backup <new-file.sqlite3>` creates and verifies a consistent SQLite snapshot. Choose an existing parent directory outside recorded projects and all Git repositories. It refuses to overwrite. Snapshots include sensitive local event data; they are not automatically uploaded or encrypted.
- `restore <backup.sqlite3> <new-state-directory>` validates and restores into a NEW directory only. All restored projects are disabled; no runtime command, service token or recording authorization is activated. Existing state is never replaced. Configure the runtime and explicitly select recording projects only if requested.
- A backup on the same device is not independent disaster recovery. Do not delete old state or migrate live recording implicitly.
